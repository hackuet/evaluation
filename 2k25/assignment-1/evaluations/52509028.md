### Task 1: Dual LED Blinker ([Task-1 LED blinking.txt](file:///home/user/Projects/HACK%20Evaluation/2k25/assignment-1/submissions/52509028/Task-1%20LED%20blinking.txt))

#### Technical Implementation
The student implemented an independent, non-blocking dual LED blinker:
```cpp
int led_yellow = 8;
int led_red = 9;

unsigned long interval_yellow = 1000;
unsigned long interval_red = 2000;

unsigned long lastTime_yellow = 0;
unsigned long lastTime_red = 0;

int state_yellow = LOW;
int state_red = LOW;

void setup(){
  pinMode(led_yellow, OUTPUT);
  pinMode(led_red, OUTPUT);
}

void loop(){
  unsigned long currentTime = millis();

  if (currentTime - lastTime_yellow >= interval_yellow) {
    lastTime_yellow = currentTime;
    if (state_yellow == LOW) {
      state_yellow = HIGH;
    } else {
      state_yellow = LOW;
    }
    digitalWrite (led_yellow, state_yellow);
  }

  if (currentTime - lastTime_red >= interval_red) {
    lastTime_red = currentTime;
    if (state_red == LOW) {
      state_red = HIGH;
    } else {
      state_red = LOW;
    }
    digitalWrite(led_red, state_red);
  }
}
```

#### Evaluation & Merits
1. **True Concurrency & Non-Blocking Design**:
   - The sketch completely avoids `delay()`. Both LEDs evaluate their elapsed intervals independently against `millis()` on every iteration of `loop()`.
   - The yellow LED toggles at $1000\text{ ms}$ intervals and the red LED toggles at $2000\text{ ms}$ intervals without interference or cumulative drift.
2. **Proper Data Types for Embedded Timers**:
   - All timing variables (`currentTime`, `lastTime_yellow`, `lastTime_red`, `interval_yellow`, `interval_red`) are declared as `unsigned long`. This correctly handles 32-bit `millis()` math and prevents overflow glitches when calculating time differences (`currentTime - lastTime >= interval`).

### Task 2: Software PWM Implementation ([Task-2 PWM.txt](file:///home/user/Projects/HACK%20Evaluation/2k25/assignment-1/submissions/52509028/Task-2%20PWM.txt))

#### Technical Implementation
```cpp
int ledPin = 9;

void pwm(int pin, int value) {
  if (value < 0) value = 0;
  if (value > 255) value = 255;

  int time = 10000; 

  int onTime = (time * value) / 255;
  int offTime = time - onTime;

  if (onTime > 0) {
    digitalWrite(pin, HIGH);
    delayMicroseconds(onTime); 
  }

  if (offTime > 0) {
    digitalWrite(pin, LOW);
    delayMicroseconds(offTime);
  }
}
```

#### Evaluation & Merits
1. **Duty Cycle Math & Modulation Principle**:
   - The function `pwm(pin, value)` successfully generates software PWM without using `analogWrite()`.
   - The duty cycle formula accurately models the relationship:
     $$T_{on} = T_{total} \times \frac{value}{255}, \quad T_{off} = T_{total} - T_{on}$$
   - The total period chosen is $10{,}000\ \mu\text{s}$ ($10\text{ ms}$), creating a $100\text{ Hz}$ carrier frequency, which is suitable for LED persistence of vision.
   - Input clamping (`if (value < 0) value = 0; if (value > 255) value = 255;`) prevents out-of-bound duty cycles.
2. **Critical Embedded Bug: 16-Bit Signed Integer Overflow on AVR**:
   - The variables are declared as standard 16-bit signed `int` on 8-bit AVR microcontrollers (ATmega328P / Arduino Uno):
     ```cpp
     int time = 10000; 
     int onTime = (time * value) / 255;
     ```
   - On AVR, `int` is 16 bits with a maximum value of $+32{,}767$.
   - When evaluating `(time * value)`, the multiplication is carried out in signed 16-bit arithmetic:
     - For $value = 3$: $10000 \times 3 = 30000 \le 32767$ (valid).
     - For $value = 4$: $10000 \times 4 = 40000 > 32767$, which overflows to signed negative $-25536$, resulting in $onTime = -100$.
     - Because $onTime \le 0$, the condition `if (onTime > 0)` fails, skipping the ON pulse completely!
     - Furthermore, $offTime = time - onTime = 10000 - (-100) = 10100$, causing severe pulse distortion.
   - *Rubric Specification*: The rubric explicitly specifies:
     > *"Microsecond timing and proper duty cycle: $T_{on} = T_{total} \times \frac{value}{255}$: 21–25 / 25 (deduct 3-4 pts for 16-bit signed AVR integer overflow or edge clamping bugs)."*
   - Consequently, an objective deduction of 4 points is applied under the rubric.
3. **Simulation Verification**:
   - [`Task-2 Screen Recording.mp4`](file:///home/user/Projects/HACK%20Evaluation/2k25/assignment-1/submissions/52509028/Task-2%20Screen%20Recording.mp4) demonstrates the circuit wired in Wokwi with the LED connected to digital pin 9.
4. **Marking**:

### Task 3: Hardware-Accelerated Sonar Reader ([Task-3 Sonar reader.txt](file:///home/user/Projects/HACK%20Evaluation/2k25/assignment-1/submissions/52509028/Task-3%20Sonar%20reader.txt))

#### Technical Implementation
```cpp
int trigPin = 10;
int echoPin = 9;

long duration;
float distance;

void setup() {
  pinMode(trigPin, OUTPUT);
  pinMode(echoPin, INPUT);
  Serial.begin(9600);
}

void loop() {
  digitalWrite(trigPin, LOW);
  delayMicroseconds(2);
  digitalWrite(trigPin, HIGH);
  delayMicroseconds(10);
  digitalWrite(trigPin, LOW);

  while (digitalRead(echoPin) == LOW); 
  long startTime = micros();

  while (digitalRead(echoPin) == HIGH); 
  long endTime = micros();

  duration = endTime - startTime;
  distance = duration * 0.034 / 2;

  Serial.print("Distance: ");
  Serial.println(distance);
  Serial.println(" cm");

  delay(100);
}
```

#### Evaluation & Merits
1. **Pulse Timing & Physics**:
   - The trigger pulse sequence follows the HC-SR04 datasheet: $2\,\mu\text{s}$ LOW baseline, $10\,\mu\text{s}$ HIGH acoustic transmit trigger, and LOW idle.
   - The round-trip acoustic equation properly applies the speed of sound in air ($0.034\text{ cm}/\mu\text{s}$) divided by 2:
     $$\text{Distance} = \frac{\text{duration} \times 0.034}{2}$$
2. **Custom Edge Polling vs. Hardware Acceleration**:
   - The student successfully avoids `pulseIn()` by capturing edge transitions using `while` polling and `micros()`.
   - However, **true hardware acceleration** requires asynchronous hardware interrupts (e.g. Timer1 Input Capture Unit `ICP1` or Pin Change Interrupts `PCINT`), which offload edge timing completely from the CPU core.
   - The student's implementation uses CPU busy-waiting loops:
     ```cpp
     while (digitalRead(echoPin) == LOW); 
     while (digitalRead(echoPin) == HIGH);
     ```
   - **Vulnerability (Infinite Blocking)**: These tight `while` loops lack a timeout mechanism. If an echo pulse is lost (e.g. out of range, signal absorbed, or wire disconnected), the microcontroller hangs indefinitely in the `while` loop, crashing real-time system operation.
3. **Rubric Alignment**:
   - The rubric specifies:
     > *"Interrupt-driven (Timer1 Input Capture / PCINT): 25 / 25."*
     > *"CPU-polling edge timing using `micros()` (without `pulseIn()`): 16–20 / 25."*
   - Because the student implemented CPU-polling edge timing without `pulseIn()`, but lacks timeout protection and hardware interrupts, the LLM awards **18.00 / 25** (within the 16–20 bracket).

### Recommended Next Steps for Technical Growth

1. **Beware of 16-Bit Architecture Integer Overflows**:
   - On 8-bit AVR microcontrollers like the Arduino Uno (ATmega328P), an `int` is 16 bits ($-32{,}768$ to $+32{,}767$).
   - When multiplying large constants like $10{,}000$ by an 8-bit variable ($0 \dots 255$), the result ($0 \dots 2{,}550{,}000$) immediately exceeds 16 bits.
   - *Fix*: Declare `time` as `unsigned long` or explicitly cast the calculation:
     ```cpp
     unsigned long time = 10000;
     unsigned long onTime = (time * (unsigned long)value) / 255;
     ```

2. **Add Timeout Guards to All Sensor Polling Loops**:
   - Never trust an external sensor to pull a pin HIGH or LOW indefinitely. If an ultrasonic pulse misses the sensor, `while (digitalRead(echoPin) == HIGH);` locks the entire board forever.
   - Always include a microsecond timeout guard (e.g., $30\text{ ms}$ for HC-SR04, corresponding to $>400\text{ cm}$):
     ```cpp
     unsigned long startWait = micros();
     while (digitalRead(echoPin) == LOW) {
       if (micros() - startWait > 30000) return -1.0; // Timeout error handling
     }
     ```

3. **Advance to True Hardware Acceleration via Timers and Interrupts**:
   - **For PWM**: Utilize the hardware Timer1 registers (`TCCR1A`, `TCCR1B`, `OCR1A`) to generate hardware PWM directly on pin 9 at 16 MHz with **zero CPU utilization**.
   - **For Sonar**: Use Timer1 Input Capture (`ICP1` on Pin 8) or Pin Change Interrupts (`PCINT`) to record the exact clock cycle of rising and falling edges in hardware without any polling loops.
